가명처리 요청을 한다고 가정
1. gui에서 api_gateway/pseudonymization 으로 api 호출
2. pseudonymization() 메소드에서는 producer 객체를 통해 "pseudo_topic"에 파일 전달
3. psedunymization_server는 consumer 객체를 통해 pseudo_topic에서 파일 가져와서 가명처리
4. pseudonymization_server의 producer 객체를 통해 pseudo_result_topic에 가명처리 파일 전달
5. pseudonymization() 메소드는 consumer 객체를 통해 pseudo_result_topic에서 값을 가져와서 처리..

ag에서 id=1에 해당하는 요청을 pt에 적재 요청(producer)
동일하게 id=1에 해당하는 요청을 prt에 요청(consumer)

의도: producer로 전달한 파일이 내부적으로 가명처리 돼서 consumer로 요청할 때 가명처리된 파일로 가져와 지는 것
현재 동작: producer로 전달한 파일 A가 가명처리 되는것 까지는 OK, 하지만 consumer로 요청되면 FIFO를 기준으로 동작하기 때문에 [A]만 있을 경우는 정상 동작
but, [B, A] 순으로 적재된 경우 consumer가 request를 하면 B를 반환해줌...

producer.request(topic name, message id, payload) 형태로 전달 해야 함

broker는 이를 받아서 topic name에 해당하는 topic에 { message id: payload, ... } 형태로 값을 저장함

ConcurrentLinkedQueue<MemoryRecord>가 아닌 ConcurrentHashMap<UUID, ConcurrentLinkeQueue<MemoryRecord>> 형태로 저장하는 것은 어떨까?

예를 들어
UUID == message id라고 가정하고, a 유저가 보는 gui에서 가명처리 요청을 보내는 상황이면 a.producer.request(t1, a, file1) 형태로 보내게 되면,
broker는 이를 아래 형태와 같이 저장할거야.

map = {
    a: (file1), ...
}

그리고 다시 가명처리 완료된 파일을 획득하기 위해 t2를 구독한다면, a.consumer.request(t2, a) 형태로 구독하게 되는거지.

이렇게 map으로 관리하는 이유는, 동적 토픽 생성을 제한하기 위함이야.

왜냐하면, a 이외에 클라이언트가 t1에 값을 생산하게 될 경우, a가 생산한 가명처리 대상 파일이 b가 생산한 가명처리 대상 파일과 동일한 토픽 t1에 저장될 것이고,
가명처리 서버는 t1 토픽에서 값을 가져오면 이게 a거인지 b 거인지 상관없이 가명처리한 뒤 t2에 결과를 저장하게 될거야.
이렇게 되면 a와 b는 t2에서 값을 꺼내게 될 경우 원래 자기거인지를 모르는거지.

이를 해소하기 위해서는 a_t1 b_t2을 생성해야 하는데(처음부터 분리) 이럴 경우 가명처리 서버는 클라이언트가 늘어남에따라 소비를 위해 구독해야하는 토픽이 계속 증가하게 되버림
따라서 토픽 구조를 queue가 아닌 map으로 하고 가명처리 서버가 t1만을 구독하면 t1 내부에서 a의 queue 값을 꺼내서 처리했다면 t2에도 a에 값을 넣고, ... 를 하게 되는거지

consumer.requets()는 기본적으로 topic name과 message id를 전달 받게 되는데(request(topic name, message id)) 만약 message id가 null일 경우에는
topic name에 해당하는 토픽에서 a, b, .. 와 상관없이 아무 queue에서 값을 꺼내오는데 대신 값은 Map("a" or "b" or ..., MemoryRecord@xx) 형태로 전달되게 돼.

달리 말하면, topic name, message id를 모두 전달한 경우에는 topic name에 해당하는 topic에서 message id에 해당하는 큐에서만 값을 꺼내오게 되는거지
즉, message id를 지정하게 되면, 특정 클라이언트에 1:1 대응되는 "전용 처리자"를 붙이게 되는거고, message id를 지정하지 않게 되면 모든 클라이언트에 대한 n:1 처리자가 돼서
처리하게 되는거지.

netty_client.request()는 기존 (type, message)에서 (type, message, id)를 전달받도록 변경, reuqest id는 삭제해도 무방할듯..?
